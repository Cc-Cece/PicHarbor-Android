# PicHarbor 移动端统一总体方向任务书

日期：2026-11-12  
状态：总体架构方向已确定，具体技术选型与实施方案待评估。

## 1. 背景与目标

维护者主要使用 iOS，安卓用户仍需要持续支持。分别维护两套完整业务实现，会增加功能同步、问题定位和回归验证的成本。

本项目采用“共享业务逻辑，分别使用原生 UI”的方向：以现有 iOS 为功能、交互流程和业务行为的主要蓝本，逐步建立两端共同使用的业务核心，同时保留各端原生界面与必要的系统适配。

目标是让通用业务规则只维护一份，使 iOS 日常使用中发现并修复的业务问题能够同时惠及安卓；平台行为仍分别验证。

## 2. 已确定的原则

1. iOS 保留 SwiftUI 界面，尽量维持现有外观、导航与操作习惯。允许为连接共享层调整数据绑定和调用方式。
2. 安卓继续使用原生 UI，接入统一业务能力；界面可以遵循安卓习惯，不要求与 iOS 像素级一致。
3. 共享层负责业务决策，原生 UI 负责展示与用户输入，平台适配负责执行系统操作。
4. 以 iOS 的功能和行为为主要参考，但不把现有全部实现直接视为正确标准。实验能力、已知问题和未经实机验证的行为必须单独标记。
5. 旧安卓项目作为辅助参考，重点继承系统适配经验、诊断日志规范及构建发布能力，不为了复用旧代码牺牲统一后的边界。
6. 逐步迁移，每个阶段提供可构建、可验证的两端结果，避免长期只形成无法运行的共享框架。
7. 本任务书确定方向，不代表已批准具体技术框架、仓库迁移、包名调整或发布切换。

## 3. 共享与平台职责

| 范围 | 目标职责 | 迁移要求 |
| --- | --- | --- |
| 任务模型与状态 | 任务标识、生命周期、状态转换、用户操作语义 | 建立唯一业务定义，两端不得各自推导完成状态 |
| 备份业务规则 | 去重、重试、暂停与恢复、提交、云端确认 | 抽出平台无关决策，系统调度与传输通过接口执行 |
| 清理规则 | 清理资格、云端证据、风险确认、失败处理 | 共享判定，原生执行系统删除；未经充分确认不得清理原件 |
| 协议核心 | Google Photos 协议、结果解析与错误分类 | 尽量复用 Python 实现，消除平台耦合，避免两端长期维护分叉 |
| 界面状态 | 进度、任务摘要、可用操作、错误码和必要展示数据 | 由共享层提供语义一致的状态，各端负责本地化与呈现 |
| 持久化与恢复 | 数据模型、版本、恢复规则及一致性要求 | 统一语义；具体存储实现和旧数据迁移方式待评估 |
| 日志 | 事件语义、关联标识、脱敏、保留与导出约定 | 统一规范，平台采集与文件分享分别适配 |
| iOS 系统能力 | PhotoKit、Live Photo 资源导出、后台 URLSession、钥匙串、自签刷新 | 尽量保留已有原生实现，通过明确接口接入 |
| 安卓系统能力 | 媒体访问、权限、后台任务、安全存储、系统删除 | 实现对应平台适配，按需复用旧安卓经验 |
| 原生 UI | 页面、导航、动画、系统交互 | SwiftUI 与安卓原生 UI 分别维护，不承载重复业务决策 |

共享业务核心的语言和运行方式尚未确定。Kotlin Multiplatform 只是候选方案，不能视作已选定。Python 保留范围也需要结合线程、生命周期、构建和性能验证确定。

## 4. 关键边界要求

- 共享核心不能直接依赖 SwiftUI、Android Context、PhotoKit 或 WorkManager 等平台对象。
- 平台通过接口提供媒体资源、文件传输、凭据访问、持久化及系统执行结果；共享核心据此推进业务状态。
- 后台任务完成、应用重启和系统重新唤起时，应能重新关联原任务并继续确认；不得依赖某个页面或内存对象持续存活。
- 同一任务的重复回调、重试和恢复必须具备幂等处理，避免重复提交或错误标记成功。
- 状态、错误码与接口应有版本和兼容规则。原生 UI 不得仅根据 HTTP 成功或字节传完判定备份成功。
- 区分业务暂停、系统暂挂、等待网络、失败和等待云端确认，确保两端含义一致。

## 5. 日志方向

以此前安卓诊断体系为基础，形成两端统一的事件和导出规范：

- 默认持续记录，不提供手动关闭或保留参数配置。
- 保留上限为 14 天或固定总大小，任一达到即滚动清理。安卓现有实现为 64 MiB，统一版的大小上限在详细设计中确认。
- 设置中提供导出入口，允许选择日期区间，默认全部现存日志。
- 导出内容同时便于开发者、AI 和用户阅读，保留结构化事件及可读文本。
- 通过会话、任务、资源和操作关联标识，串联业务核心、Python 协议和平台执行过程。
- 不记录照片或视频本体，不记录明文密码、令牌、账号标识及其他凭据；文件名可按既定需求保留，并在导出说明中准确披露。
- 脱敏应覆盖运行时写入及导出内容，不能仅靠用户说明。诊断应能区分业务、协议、存储、权限、系统调度和网络问题。

## 6. 分阶段任务与交付物

### 阶段一：盘点与技术验证

交付两端功能清单、行为差异、稳定及实验能力清单、业务与平台依赖图，并确定共享核心候选方案。

技术验证至少覆盖：两端调用共享核心、异步状态通知、Python 桥接、取消、原生后台任务回调、应用重启后的恢复，以及现有构建发布链路的接入。

依据验证结果确定技术选型、模块划分、存储方案和仓库组织，并记录取舍依据。不以代码复用比例作为唯一标准。

### 阶段二：普通照片备份完整流程

先迁移任务模型、错误码和基础日志，完成“选择普通照片 → 去重与准备 → 原生传输 → 提交 → 云端确认 → 展示结果”。

iOS 使用现有 SwiftUI 接入，安卓提供原生界面接入。同阶段验证暂停、断网、失败重试与进程重启后的恢复。

### 阶段三：逐步覆盖现有功能

依据功能清单，逐步迁移批量任务、相册范围、视频、资源复用、清理、代理和电脑直连等既有能力。Live Photo 及其他实验能力单独验收，不能直接继承“已支持”的结论。

每批功能迁移后，明确新旧实现的职责和切换方式，防止长期维护两套活动业务核心。

### 阶段四：数据迁移与发布切换

验证旧数据、设置、凭据和未完成任务的兼容或迁移方案，提供用户可理解的升级说明与失败处理路径。

两端分别完成构建、安装、升级与实机验收后，再执行发布切换及旧实现退出计划。

## 7. 核心验收标准

1. 两端相同输入和业务事件产生语义一致的任务状态与错误结果。
2. 通用业务规则的修改不需要在 Swift 和 Kotlin 中分别实现一次。
3. iOS 现有主要界面和交互可以保留，安卓原生界面能够接入相同业务状态。
4. 重复回调、断网、暂停、进程结束和重启恢复不会导致重复提交、任务丢失或虚假成功。
5. 备份完成必须包含所需的云端确认；无法确认时保留原件并展示明确状态。
6. 两端分别验证媒体权限、后台执行、资源读取和系统删除；iOS 通过不能替代安卓验收。
7. 导出脱敏日志能够关联完整任务过程，并定位故障阶段；凭据与媒体本体不进入日志。
8. 迁移后仍可分别构建与发布 Android APK 和 iOS IPA，平台专属能力不因共享层接入而失效。

测试优先覆盖状态转换、幂等恢复、清理条件与接口契约等高价值行为。实施时优先完成可运行代码，再执行必要验证，不以大量形式化测试替代实际功能完成。

## 8. 用户兼容与发布约束

- 新架构本身不要求更改 Android applicationId 或 iOS Bundle Identifier。
- 安卓后续发布沿用 v1.0.9-beta.5 的固定签名密钥，并保留构建前后签名校验。私钥和密码不得提交仓库。
- GitHub 原 v1.0.8 与当前 beta.5 签名不同，不能直接覆盖安装。共享架构迁移不会自动解决这一签名限制。
- 是否采用新包名共存、如何迁移旧数据以及何时停止旧版支持，需要单独确定；此前讨论共存不等于已经决定执行。
- 未明确授权并准备迁移方案前，不卸载旧应用、不清除用户数据、不执行不可逆的数据转换。

## 9. 待决定事项

1. 共享核心的语言、框架、Python 保留范围和桥接方式。
2. 统一仓库的位置、模块结构及两端构建发布组织方式。
3. 数据库与任务恢复实现、旧数据兼容策略。
4. 各现有功能的准确支持范围、实验标记和迁移顺序。
5. Android 包名与旧签名用户的迁移方式。
6. 统一日志大小上限和平台事件补充规范。
7. 安卓实机验收方式、版本切换及旧版支持安排。

## 10. 当前任务边界

本次交付为总体方向任务书。下一步应完成阶段一的盘点和可运行技术验证，再依据证据形成详细实施计划。本文件不代表已经完成共享架构、决定发布日期或承诺零平台维护成本。
