# Android Bug 确认、定位与修复验收流程

状态：设计规范，配套功能尚未实现。主方案见 [README](README.md)。

## 1. 用户侧最短流程

常驻基础日志负责保留首次故障，不能要求用户事先预测问题。

1. 日志始终开启；异常观察器自动生成 incident ID 并冻结现场，用户无需点击录制或标记。
2. 用户遇到异常，进入设置，点击唯一的“导出日志”按钮。导出面板日期范围默认“全部”，也可选择起止日期，再通过系统文档选择器保存 ZIP。
3. 不强制用户选择日期，不提供日志等级、账号筛选或问题表单；不提供关闭、增强录制、保留时长和容量配置。日期只控制本次导出。
4. 若 App 已闪退，重开后仍可从同一设置入口导出；在固定 14 天/64 MiB 限制内关联上一 session，不能因新会话创建就丢掉上一事故。
5. ZIP 同时包含控制台风格 readable.log、所选范围内的 events.jsonl、摘要与现场附件；用户自行决定如何分享和描述现象。自动提示范围为空或部分已被覆盖。
6. 需要复现时，维护者先保留原包，再指导单变量实验；用户不必配置日志，每次实验通过任务 ID、时间和配置快照关联。

设置页只显示“导出日志”按钮及主方案规定的脱敏/保留说明；引擎失败、账号未登录或备份线程卡住时仍可进入和导出。不在每个网络重试时弹窗，也不新增诊断提醒入口。

## 2. 报告接收与证据等级

维护者为反馈创建 case ID，记录 bundle/incident ID、应用 build、时间范围、症状、影响和用户复现说明。用户分享完整包到受控渠道，公共 Issue 使用脱敏摘要。缺少包时仍可建单，不因没有日志直接关闭。

| 阶段 | 进入条件 | 必须产出 | 不能混淆 |
| --- | --- | --- | --- |
| 已收到 | 有症状描述 | case、影响、版本、待补字段 | 用户反馈不等于已复现 |
| 待补证据 | 缺关键版本/现场/时序 | 最少补充动作及原因 | 不让用户无限收集无方向日志 |
| 已确认异常 | 包或复现证明行为违反预期 | 预期/实际、事件/快照引用、证据缺口 | 卡住已确认不等于根因确定 |
| 根因假设 | 已缩小故障范围 | 假设、支持/反对证据、区分实验 | “可能网络”不能算根因 |
| 根因已验证 | 区分实验或代码与运行证据闭环 | 触发条件、机制、最小复现或等价注入 | 无法复现须明确标记置信度 |
| 待回归 | 修复完成 | 关联改动、回归矩阵、构建和测试结果 | 发布了新包不等于修好了 |
| 已验证解决 | 同触发条件旧版失败、新版通过，且无关键行为回归 | 对照结果、剩余限制、必要的用户回访 | 若只能缓解，标“缓解”，不宣称根治 |

无硬件无法完成用户原环境验证时，记录“注入场景通过、原设备待确认”；允许保留为监测中，不能制造确定性。

## 3. 开发者离线分析工具要求

后续实现 `tools/analyze_diagnostics.py`，本次仅定义接口，不声称命令已可运行：

```text
analyze_diagnostics <bundle.zip> --summary
analyze_diagnostics <bundle.zip> --trace <trace_id>
analyze_diagnostics <bundle.zip> --incident <incident_id>
analyze_diagnostics <bundle.zip> --check-invariants
analyze_diagnostics <old.zip> --compare <new.zip>
```

工具必须能离线使用，不上传包，不执行包内代码。检查路径穿越、symlink、压缩炸弹、文件总大小/数量/解压比上限；不信任 manifest 声明的大小。先流式验证成员哈希和 Schema，再按 producer sequence 重建时间线。受损或未知版本生成 partial 结果，不静默当作完整。

输出至少包含：

- 构建和配置差异，生效配置与 UI 设置的差异。
- 每条项目/请求链的阶段时长、最后观测事件、未闭合 span、重试与取消预算。
- 在途操作和 owner/waiter 图、并发名额守恒、队列是否具备运行条件。
- 各 session 的关联与系统退出信息；跨 boot 不计算单调时长。
- 任务/字节计数守恒、业务 revision 与 UI revision 是否分叉。
- 证据质量：缺口、采样、未知发送量、缺失栈、未知云端结果。
- 带事件引用的事实、候选原因、可以推翻该原因的下一次实验。规则匹配不叫“自动根因确定”。

错误聚类 fingerprint 使用规范化 error code、endpoint/stage、顶部符号帧、引擎/协议版本；不使用文件名、账号、设备序列号。旧/新版本比较必须展示网络、文件集合、设备和策略差异，不能将不同实验直接视为对照。

## 4. Issue #2 专用排查剧本

收集时不要先强制更换网络并丢失原现场。记录 App/Android/机型、并发、超时、重试、代理类型、前后台、卡住时长；导出一次卡住现场和一次重启后的恢复现场。

1. 找最近 `incident.opened`，检查 coverage 和 logger health，确认日志是否覆盖故障发生之前。
2. 找全部在途项目，不只看 UI 最近显示的文件。查看每个 permit owner 和正在等待的项目。
3. 根据请求/operation start/end 确认最后观测范围：本地读取、云端查重、取令牌、body、commit、相册、DAO 或 callback。
4. 比较两次快照：是否有真实字节、远端确认或任务 revision 推进；日志心跳/重试计数增加不算上传推进。
5. 看 Java/Python 栈与等待图是否支持具体阻塞；没有栈就保持“范围定位”，不能给出死锁结论。
6. 核对请求超时与实际 client 配置，重试之间是否有返回，取消有没有被观察以及 worker 是否真正退出。
7. 再做同一批非敏感文件、并发 1 与 2、同一代理/另一合法网络路径的单变量对照，记录实验 ID；照片/视频分组只在前述证据指向文件时做。
8. commit 结果 unknown 时先核对云端，避免把重传后没有重复误当作先前一定失败。

确认根因的示例：旧版两个 HTTP 请求同时阻塞且无法在预算内退出；相同注入在新版能采证并正常退出，名额归还，队列继续，且没有两个实际存活 worker 处理同项目。仅“重启后好了”不符合这个标准。

## 5. 验收矩阵：必须主动制造故障

测试必须用受控 transport、文件提供方或测试设备注入，覆盖正式混淆包；不能只测试 logger 的 write 函数。每行至少产出一个可供分析器读取的黄金包与预期事实列表，日志不能把注入参数直接写作诊断结论。

| 注入场景 | 必须看到的证据 | 通过标准 |
| --- | --- | --- |
| DNS/连接/TLS 失败 | endpoint、异常分类、request、实际能力、重试预算 | 可区分已观测错误；无底层能力时诚实标 unknown |
| body 读取正常但传输 API 不返回 | start、source read、未知发送量、permit owner、双快照 | 可定位到 body API 范围；独立采证、导出可用 |
| 服务端间歇返回少量数据导致总耗时超出读超时 | 请求起点、响应进展和超时配置 | 不把 timeout=60 解释成总耗时 60 秒 |
| 上传后 commit 响应丢失 | body end、commit start/error、outcome unknown | 分析器不宣称失败、不建议无条件重传 |
| 429/503 与退避 | status、Retry-After、预算、等待开始/结束 | 区分合法退避与无进展；没有伪卡顿警报 |
| 两个并发请求卡住 | 两个 attempt、permit owner、队列深度 | 能解释为什么后续项目不启动 |
| 同内容锁等待/生命周期写者等待 | wait start、owner、请求 span | 不将锁等待误判为网络慢 |
| callback/DAO 卡住 | callback/transaction start、Java/Python 边界 | 网络已结束的证据与本地阻塞范围可分开 |
| UIDT 接受但未启动、兜底同时启动 | submitted/accepted/started/fallback、run | 能识别调度缺口与 runner 竞争 |
| Wi-Fi→蜂窝/VPN 切换，省电约束，休眠再恢复 | network/lifecycle/constraint/gap | 等待原因可见；休眠不当作持续活跃卡死 |
| SAF 提供方卡住、权限撤回、源文件变更 | source kind、open/read、权限、前后元数据投影 | 与 HTTP 卡住可区分；无真实 URI/路径 |
| FD/临时资源泄漏 | handle open/close、资源趋势、事故快照 | 能找未闭合 handle；不扫描整个媒体库 |
| 取消请求遭延迟 | requested/observed/completed、存活 worker | 不能用日志“取消完成”掩盖后台仍运行 |
| 强杀/ANR/Java crash/native crash/内存压力退出 | 上个 session、退出补采和 coverage | 有系统证据才分类；Android 10 降级明确 |
| UI 进度停住、后台真实推进 | UI revision、任务 revision、心跳 | 能判断显示滞后，避免误诊上传停滞 |
| Live Photo 一半失败/确认延迟 | logical item、两个 resource、commit/confirm | 区分单资源完成与整对确认 |
| 清理核验不充分、系统授权取消、删除部分失败 | evidence/policy/consent/reconcile | 不将上传成功当作可删除，不将授权当实际删除 |
| 桌面链接断线、offset 不一致、对端无回执 | transfer/session、offset、校验/receipt | 本端只能判已发送或未知，不能冒称对端落盘 |
| 日志磁盘满、writer 卡住、队列溢出 | 应急 health、丢失计数、partial manifest | 业务不因 logger 阻塞；基本摘要仍可输出 |
| 强杀发生在写半行、导出时业务仍在写入 | 序列缺口、cutoff、尾行损坏标记 | 包仍可读，不声称原子一致快照 |
| 时钟回拨、设备重启、乱序/重复事件 | wall/mono/boot、event ID | 无负耗时、无跨 boot 计时、可去重 |
| 凭据/账号/签名 URL 混进异常或第三方日志 | 秘密哨兵覆盖 cause/header/body/stack/文件名 | 本地日志、应急文件、ZIP 均不得含秘密哨兵；普通文件名允许保留 |
| JSONL 转为控制台文本 | 相同 event ID、时间、关联字段与脱敏值 | readable.log 可追溯原事件，无额外敏感数据、无重新猜测的错误结论 |
| 达到 14 天或 64 MiB 任一条件 | 淘汰记录、真实覆盖范围、partial 原因 | 自动滚动且无需用户操作；事故、临时和应急文件不能绕过限制 |
| 默认全部、自定义首尾日期、跨日/时区/夏令时 | 所选日期、固定时区、UTC 半开边界、实际覆盖 | 默认导出所有保留记录；自定义包含首尾当天，两份日志相同筛选，无区间外事件 |
| 区间无日志/部分已覆盖、跨区间 span 与事故 | 空范围提示、实际交集、excluded_by_date_range | 无空包假成功；裁剪不误报为卡死；不为补上下文悄悄导出区间外事件 |
| 升级/旧版任务/未知事件版本 | schema/catalog、legacy coverage、迁移记录 | 不崩分析器、不伪造历史事件 |

## 6. 性能与数据质量门槛

首版验收预算，需固定设备、网络、测试集合做至少 3 轮对照，记录方差；不是当前已测结果：

- 默认日志使备份吞吐中位数下降不超过 3%，额外峰值内存不超过 10 MiB；超出需优化或明确评审预算。
- 事件 emit 不做文件/网络 I/O、不等待业务锁；目标 p95 <1ms，记录 p99 与最大值。冷启动额外开销目标 <30ms。
- 正常基础日志除单个长操作边界外，progress 每在途项 10 秒最多一条；10 万项目扫描需受聚合策略约束，不允许每个 chunk 落盘。
- 诊断目录始终满足固定 64 MiB 上限与子预算，读取/导出前排除过期记录；2 倍预计峰值事件流持续 10 分钟不得使内存无限增长。设置中无关闭或调整保留策略的入口。
- 活跃执行且规则条件持续成立时，事故记录在阈值后 10 秒内出现；系统未调度进程时不作此保证。
- 模拟 Python GIL 或上传线程阻塞，Kotlin 观察器仍输出 last-known snapshot；导出器 5 秒内尽力给出摘要/缺失原因，不能等待业务解锁。
- 正常完成的每个 span 有一个结束事件；缺失必须能由损坏/丢弃/退出证据解释。故障包中的在途 span 允许无结束。
- 事故中的所有 ERROR、状态和 request ID 均可追溯到 task/attempt 或明确的 app root；跨语言关联黄金样例 100% 通过。
- 发布版 R8 栈可用归档 mapping 还原到指定源码版本；缺映射的构建不视作满足诊断验收。
- 脱敏哨兵测试和包路径/配额校验属于发布阻断项。吞吐预算不达标也不得用删除关键故障边界事件解决。

## 7. 实施顺序与交付门槛

| 里程碑 | 工作内容 | 出口标准 |
| --- | --- | --- |
| M0 契约固定 | 补完事件专属类型/枚举、schema、错误码映射、黄金样例、版本规则 | Kotlin/Python 对相同样例解析结果一致；敏感字段注册审核完成 |
| M1 基础 recorder | 会话/时钟、类型事件、白名单、writer/轮转/health、最小导出 | 正式混淆包能离线导出；磁盘满和敏感哨兵测试通过 |
| M2 上传链路闭环 | Engine/HTTP/source/locks/permits/retry/cancel/persist、独立观察器 | #2 范围内所有注入能区分；卡住时仍可采证和导出 |
| M3 生命周期及业务覆盖 | 调度/退出/恢复、清理核验/删除、配对、UI revision | 第 5 节业务矩阵通过，未知/不支持能力清楚显示 |
| M4 分析与发布 | 离线分析器、摘要、符号归档、用户流程、性能实测 | 陌生维护者仅凭黄金包可给出预期事实和下一步；全部门槛通过 |
| M5 真实场景试用 | 小范围真实长队列、代理、前后台和机型组合试用 | 不依赖开发者手动开 Logcat；至少收集一次首次故障完整包及恢复包 |

M1 只是能写日志，不能对外称完整诊断体系；至少 M2 才解决上传定位缺口，M4 才满足完整交付。恢复算法和自动中断/重试属于独立改动，必须在旧行为有证据后实施。

建议先创建一项 Android 总任务和 M0–M5 子任务；本次不代为创建 GitHub Issue、不修改业务代码。每个后续 PR 说明新增事件、隐私字段、黄金样例和本矩阵覆盖项，新增业务阶段没有对应诊断边界则不能算完成。

## 8. 后续迁移到 iOS / 桌面端

Android 验收稳定后，把 schema、事件专属注册表、黄金包、错误语义和离线分析器提取为有版本的共享契约。Swift/C# 适配器必须通过相同 conformance fixtures；系统特有能力留在 coverage 和平台命名空间，不能分别发明 upload/commit/retry 的含义。

迁移不要求立刻共享 UI 或后台执行器。先比较 iOS 现有阶段租约和 Android 新语义的对应关系，保留已经更完整的恢复/确认机制；桌面端随后解决 Python 子进程与宿主关联。未改造对端可正常传输，仅关联证据能力降级。
